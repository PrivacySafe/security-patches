# Changelog

Notable changes to PrivacySafe Security Patches, newest first.

## 2026-10-30

### New

- Every README ends with the same footer (important notice, support, contributing, more from PrivacySafe, license), kept in step by `packaging/readme-footer.py`. The documentation site draws a solid, one-color icon for each emoji in the READMEs, and `check-site.py` now also fails a page with a leftover emoji or a tool page that lacks a part the others have.
- The documentation is online at [privacysafe.app/docs/security-patches](https://privacysafe.app/docs/security-patches/), in the PrivacySafe design with the privacysafe.app header, footer and metrics. It has an Atom feed of the newest advisories (`feed.xml`), a sitemap, and sits in a `/docs` section beside the PrivacySafe app guides, the VPN setup guide, the Social guide and the 3NWeb protocols. `gen-site.py --theme privacysafe-app` builds it.
- A documentation site, built from the READMEs: a home page that starts with the newest vulnerabilities, tools grouped by kind of software, a CVE index, a short guide to how the tools work, a glossary of the terms the pages use, the install guide, one page per tool with an at-a-glance box (who is affected, the fix, the severity, whether it is exploited, which CVEs, which commands only read and which change something, the command to run, and related tools), a filter for tools that can protect the machine, one page per manual page, the changelog and the policies, with a search that works offline. The offline copy loads nothing from other sites. It loads nothing from other sites and has no tracking. It is in [`site/`](site/) and the packages install it under `/usr/share/doc/psf-security-patches/html`.
- Manual pages and an info manual. Every script now has a page (`man psf-haproxy-check`), there is an overview (`man psf-security-patches`) and the same material is available as `info psf-security-patches`. The deb and rpm install them, and their descriptions are rewritten in plain language and list the newer tools. Each page names the AI assistance recorded in the script's header.
- [vsftpd](vsftpd/README.md#vsftpd-ftps-data-channel-hijack): a check for CVE-2026-119568, the FTPS session ticket flaw, and for CVE-2025-14242, a denial of service in Red Hat family packages. `mitigate` turns off `pasv_promiscuous`, can require client certificates and can limit who reaches the FTP ports (see [Mitigating it](vsftpd/README.md#mitigating-it)). `harden` is optional baseline hardening. `rollback` undoes both.
- [Claude Code extension backdoor](claude-code-vsx/README.md#claude-code-extension-ssh-backdoor): check, hunt, clean-up and a firewall block for the tampered extension that Cursor's marketplace served on 29 October. It works on macOS and GNU/Linux.
  - `update` [installs the vendor's fixed build](claude-code-vsx/README.md#get-the-vendors-fix-first-then-clean) after asking. Enter means yes.
  - `keys` [lists your private keys](claude-code-vsx/README.md#ssh-keys-and-the-agent-folder): type, fingerprint, whether a passphrase protects them, and which `Host` entries in `~/.ssh/config` use them.
  - `clean` saves a record of `~/.ssh` before it changes anything. `--copy-keys` and `--drop-agent-keys` are optional.
- Protection with rollback for tools that could only check before: [HAProxy](haproxy/README.md#fixing-it), [rsyslog](rsyslog/README.md#commands), [YOOtheme](yootheme/README.md#protective-measure-deny-php-in-media-and-cache-paths), [Tomcat](tomcat/README.md#commands), [the Linux kernel local root flaws](linux-kernel/README.md#mitigation-mitigate), [Joomla](joomla/README.md#mitigation-restrict-the-administrator-path), [Django REST framework](django/README.md#protective-measure-for-the-accept-header-flaw), [Drupal core](drupal/README.md#drupal-core-check), [WordPress core (wp2shell)](wordpress/README.md#if-you-cannot-update-at-once) and [nginx](nginx/README.md#nginx-workarounds-mitigate). Each one copies a file before it edits it, checks the result with the service's own checker, puts the original back if the check fails, supports `--dry-run`, and reloads or restarts nothing unless you ask.
- [WordPress plugins](wordpress/README.md#wordpress-plugins-october-2026-check): `mitigate` deactivates OttoKit, SureCart, LatePoint, Amelia, Profile Builder or Bricksforge when it is below its fixed version. WP-CLI and drush now run as the site's owner, never as root.

### Changed

- The packages are now named `psf-security-patches` (they were `psf-security-packages`), to match the tools' folder and manual pages. The new `.deb` and `.rpm` replace the old package when you install them, so upgrading needs no uninstall.
- Defaults are decided for you. nginx `mitigate` with no option applies session tickets off and AIO off. Tomcat `mitigate` with no option applies the HTTP/2 measure. The measures that can break software (nginx request buffering, the Tomcat AJP change, user namespaces, plugin deactivation) stay opt-in.
- Every README now uses the same section names, and the wording was rewritten for people. The newest vulnerabilities are at the top of the [main README](README.md).
- Release 26.10.30-1.0.0 replaces 26.10.28-1.0.0. Every script carries the date 2026-10-30.

### Fixed

- OpenSSL check: `OPENSSL_NO_PACKAGE=1` now ignores the host's package changelog, as documented. Before, a patched system library could make an unrelated local build look fixed.

### Fixed

- [PHP session audit](php/README.md): a risky session serializer (`php_binary` or `php_serialize`) on its own, with upload progress off and no runtime switch in the code, exited `0` and printed "No precondition found", although its usage defines exit `2` as a partial match and the same run had already reported condition 1. It now exits `2` and says it is a partial match.
- [libheif checker](heif/README.md): the `policy` check judged a coder blocked when a policy file was written on one line, because one element's `rights="none"` could vouch for another element's pattern (a `delegate` or `path` policy made HEIC look blocked). Each `<policy>` element is now tested on its own. `harden`, `unharden`, `mw-harden` and `mw-unharden` put each backup in a directory named only by the second, so two runs in one second overwrote the original backup with an already-edited file. Every backup now has its own private directory (mode `0700`, which also keeps a `LocalSettings.php` copy, with its database credentials, from being world-readable). `hunt` reported clean when it could read no journal or log; it now exits `2`.
- [Collabora CODE mitigator](nextcloud/README.md): any option it did not recognize was silently ignored, so a mistyped or invented flag such as `restore --dry-run` ran a real restore. Only `--force` is now accepted and anything else exits `2`. `hunt` reported clean (exit `0`, with an "ok" line) when there was no app folder and no readable log. It now exits `2` and says nothing was searched.
- [Ruby checker](ruby/README.md): `scan` reported a clean result (exit `0`) when none of its scan paths existed, and `hunt` did the same when it could read no journal or log, so a search with no data looked like a clean one. Both now exit `2` and say nothing was read. A Discourse version such as `3.4.0.beta1` was displayed as `3.4.0.`. It is now shown in full.
- [Sentry for Next.js](sentry/README.md), [Storybook](storybook/README.md) and [Laravel](laravel/README.md): a pre-release of a fixed release (`10.75.2-rc.1`, `8.6.19-rc.1`, `12.68.0-RC1`) was judged fixed, because the status functions compared only the numeric part (and Laravel's `norm_ver` dropped the suffix). A pre-release comes before the release it leads up to, so it now reads as not fixed. A pre-release above the fixed number, and the fixed release itself, are judged as before.
- Known limit, stated in the release notes: the checkers that normalize with the shared `norm_ver` helper compare only the numeric part of a version, so a pre-release of exactly the fixed number can read as fixed in those that were not individually checked.
- [PHP2Shell on cPanel](php/README.md): a release candidate, beta or dev build of a fixed release (`8.4.27RC1`, `8.4.27beta2`, `8.4.27-dev`) was judged patched, because the version comparison sorts those after the final release although they come before it, so `check` exited 0 and `cleanup` would reduce the drop-in on a build that is not fixed. Such a build is now judged by its numeric part and reads as patched only above the fixed number.
- [eMudhra mitigation](pki/README.md): a certificate file moved out of `/usr/local/share/ca-certificates` or `/etc/ssl/certs` was kept under its bare file name, so two different files with the same name from different directories overwrote each other in the backup and `restore` would then have put the wrong certificate back. Each is now kept under a numbered name. Backup directories were named only by the second, so two runs in one second shared one and the second overwrote the first run's copy of `ca-certificates.conf`. The process id is now part of the name.
- [PHP2Shell mitigation](php/README.md): `remove` backed up the AppArmor profile, your local override and the disable link into one directory under the same file name, so each copy overwrote the previous one and the site-specific rules in the local override were lost (with a disable link present, only the link survived). Each now has its own name. Backup directories were named only by the second, so two runs in the same second overwrote the first backup. The process id is now part of the name. The message printed when the generated AppArmor profile fails to parse said "nothing installed" although the ini drop-in from step 1 had already been written. It now says what was and was not changed. The undocumented `PHP_VER` environment variable, which limits a run to one version like `--php`, is documented.
- Eight more checkers read running containers. LiteLLM, SageMaker, Apache Traffic Server, YOOtheme, the WordPress plugins checker, nginx-ui, Apache Pulsar and the OpenAPI codegen checker now look inside running docker and podman containers (`SCAN_CONTAINERS=1`, the default), by the same read-only probe and per-container isolated run, and each sends only what it reads: LiteLLM sends a one-line marker for each proxy config and only the matched image tags, so API and master keys stay in the container. Traffic Server blanks every line that does not load `magick.so` or `tsmemcache.so`. Pulsar sends only the four authorization settings it judges. The WordPress plugins checker sends only the `Plugin Name` and `Version` header lines and the file's modification time (Rank Math PRO's arrival-time test then uses the modification time alone and says so). Nginx-ui runs its two binary-signature tests inside the container instead of copying a 40 MB binary. LiteLLM and Pulsar also search `/app` and `/pulsar`, where the official images keep their configuration. The shared staging helper no longer depends on a `have()` function the script may not define (the OpenAPI checker has none, which made staging silently skip).
- Thirteen more checkers read running containers. Next.js, Sentry for Next.js, Storybook, Laravel, Django REST framework, Jupyter, Pillow, BIND, HAProxy, Tomcat, CouchDB, libexpat and Gitea now look inside running docker and podman containers (`SCAN_CONTAINERS=1`, the default). The JavaScript, PHP and Python checkers copy only the project files they need through a read-only probe (route directory names only for Sentry; `.env` is never copied, only its `DB_CONNECTION` line). The daemon checkers capture the daemon's version output and its configuration, with secrets (TSIG and RNDC keys, HAProxy passwords, keystore passwords, CouchDB admin entries, the Gitea CA key and every other `app.ini` value) redacted **inside the container** before anything is copied, then run once per container in isolation. Pillow judges a container's copy by that container's own Ghostscript. A staged symlink is never kept (`docker cp` copies the link itself, which the host-side check would then have followed). The same protection was added to the ten checkers that read containers earlier. The statements in the Tomcat and Gitea READMEs and `--help` that containers cannot be inspected were corrected.
- Web-application checkers now read installs inside running containers. The WordPress path traversal, Joomla, Magento and Mage-OS, baserCMS, Grav core and Login, Roundcube, Craft CMS and Drupal core and Webform checks find installs in running docker and podman containers by their marker file, copy only the files they read into a private temporary directory, and judge them like host installs (`SCAN_CONTAINERS=1`, the default). They run it once in the main shell and pass the copies on as ordinary directory arguments. Nothing is run in a container beyond `find` and a file copy, and `.env` and `wp-config.php` are never copied.
- Running containers are now checked by OpenSSL, Jenkins and Zammad. With `SCAN_CONTAINERS=1` (the default) the OpenSSL checker asks each running docker or podman container for its own distribution, package and `openssl version` and judges it by the container's rules (Ubuntu's fixed builds per release, the container's changelog, the upstream version where there is no package database). The Jenkins checker reads the advisory plugins' manifests inside containers. The Zammad checker reads `VERSION` under `/opt/zammad` and `/usr/share/zammad`, and never judges a container by the host's package version. They join GitLab, nginx-ui, Pulsar, LiteLLM, curl, nginx, Plex and others that already looked inside containers.
- Every README now has a "know before you run it" section. The 33 that lacked one (the newer checkers and a middle group of older ones) now list what the tool is and is not, drawn from each script's own stated scope: the fixed versions, what a version number cannot show, what it reads, which flaws are conditional, and where a hunt exists or does not.
- [LiteLLM checker](litellm/README.md): a scan path that exists but cannot be read left `check` reporting clean (exit `0`) although its usage promises exit `2` for something it could not read. It now exits `2` when nothing else is found.
- [GhostAction checker](ghostaction/README.md#before-you-run-it): `check` reported itself as a C2 indicator (exit `1`, "credentials may be stolen") when run from the directory it was downloaded to, because its own text names the domains. It also reported a clean result (exit `0`) when every scan path was missing, and its usage promises exit `2` for something it could not read: that is now implemented. `hunt` wrote `crontab -l` output to a fixed file in `/tmp`. - [Node.js mitigator](node/README.md#before-you-run-it): `status` exited `1` when the installed guard matched the shipped one, which is the healthy case; it now exits `0`.

The curl, nginx, Ruby and Brotli (Node.js scan) checks and the Node.js mitigator searched `PATH` with `command -v -a`, which is not a valid option in bash and failed silently, so only a fixed list of locations was searched. A Node.js, Ruby, nginx or curl installed elsewhere on `PATH` was reported as not present. They now use `type -a -P`.
- Pre-releases and non-version text were judged fixed. In the Brotli checker, a `node` that printed `v24.22.1-pre`, `-rc.0` or `-nightly…` was reported fixed at the fix version, and one that printed text (an error from a broken version-manager shim) was reported fixed because non-numeric text sorts after every number. The same function judges Bun, Envoy, Istio, cdxgen and the Ruby and PHP Brotli extensions. A `-dev` suffix was also damaged before it was judged (every `v` was removed from the output). All of these are now reported as unknown. The Node.js mitigator dropped a pre-release suffix the same way and now keeps it. A runtime it cannot judge on disk makes `check` exit `2`, as its README says.

Under `set -e`, an unreadable `curl` (or a `node` that printed no version) made the curl check and the Node.js mitigator stop silently after a few lines with exit `1`, so later findings, such as a vulnerable libcurl, were never reported and the status looked like "vulnerable". The PKI mitigator did the same, with exit `3`, when `openssl` failed during its certificate self-test. All three now report the problem and finish.

- [WordPress XSS2Shell checker](wordpress/README.md#wordpress-xss2shell-check): `check` and `audit` now stop with exit `2` when no URL is given, instead of relying on `curl` failing. `audit` reported a clean result (exit `0`) for a site that did not answer. An unreachable target is now an error (exit `2`), as its usage text always said. Its HTTP response bodies, which can contain an exposed `wp-config.php`, were written to fixed, world-readable files in `/tmp` and left behind when a run was interrupted. It now uses one private `mktemp` file that is removed on every exit path.

Ten check and mitigate tools (Brotli, curl, GhostAction, libheif, LiteLLM, nginx, Plex, Ruby, the Collabora CODE mitigator and the Node.js mitigator) exited `1` on a fatal error such as a mistyped command or an unknown option, although their READMEs document `2` for errors and `1` means findings. They now exit `2`. The PKI and PHP mitigators keep their own documented exit codes.

- Pipelines that could miss a match. Under `set -o pipefail`, `producer | grep -q PATTERN` can report "not found" when `grep -q` exits at its first match and the producer dies of SIGPIPE. Twelve scripts used the shape (bind, brotli, curl, drupal, heif, nginx, node, both PHP2Shell tools, pki, and both WordPress checkers), several of them against large sources: `journalctl` in the Node guard-liveness check, `rpm -q --changelog` in the cPanel PHP tool, `openssl s_client` in the PKI tool, and HTTP response bodies in the WordPress probes.
