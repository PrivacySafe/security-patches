# rhsa.py: the Red Hat advisory finder and checker

If this software is helpful, consider a donation to our 501c3 nonprofit: https://privacysafe.foundation

`rhsa.py` reads Red Hat's list of security advisories (RHSA) and does four jobs:

- **find** the advisories that name a CVE, with the stream and the package release that fixes it;
- **verify** installed packages: is this release at or after Red Hat's fix?
- keep the **Red Hat advisories** section of each tool README, and `REDHAT-ADVISORIES.md`, up to date (`docs`);
- **audit** the repository against the data (`audit`).

It is one Python 3.8 file with no dependencies. Only `fetch` and `find --live` use the network. It lives in the repository next to `gen-site.py` and `check-site.py` because the **Red Hat advisories** sections of the tool READMEs and `REDHAT-ADVISORIES.md` are generated by it: with the tool in the repo anyone can reproduce them, refresh them and audit them. The `.deb` and `.rpm` install it as `/opt/psf-security-patches/rhsa/rhsa.py`, with its data, and `man psf-rhsa` documents it, so a Red Hat family host can run `verify` after installing the package. Python 3.8 or newer is a recommended dependency of the packages, not a required one.

## On a host

```
$ /opt/psf-security-patches/rhsa/rhsa.py verify --rpm
$ /opt/psf-security-patches/rhsa/rhsa.py find CVE-2026-98432 --stream 9.6
```

The index that comes with the package covers the CVEs the tools cover, for Red Hat's list of 2026-04-01 to 2026-11-03. For a later list, or for every CVE in it, download the list and check against it directly:

```
$ /opt/psf-security-patches/rhsa/rhsa.py fetch --after 2026-04-01 --out /var/tmp/rhsa.json
$ /opt/psf-security-patches/rhsa/rhsa.py verify --rpm --list /var/tmp/rhsa.json
```

## What is here

| File | What it is |
|---|---|
| `rhsa.py` | The tool. `rhsa.py --help` and `rhsa.py COMMAND --help` list every option. |
| `placement.json` | Which advisories go into which README, and why some READMEs are left out. Edit this, not the READMEs. |
| `data/rhsa-index.json` | The index the tool works from: the advisories for the CVEs the READMEs name, built from Red Hat's list of 2026-04-01 to 2026-11-03. |
| `README.md` | This page. |

The tests are `internal/tests/rhsa_test.sh.txt` in the big zip of the release (they are not in the repository).

## Find

```
$ rhsa.py find CVE-2026-98432 --stream 9.6
CVE-2026-98432: 1 advisory
  RHSA-2026:94438  2026-11-03  Critical  RHEL 9.6           kernel-5.14.0-570.154.1.el9_6

$ rhsa.py find CVE-2026-92392
CVE-2026-92392: 2 advisories
  RHSA-2026:80349  2026-10-11  Important Hummingbird        rust-1.99.0-1.hum1
  RHSA-2026:82895  2026-10-14  Important Hummingbird        curl-8.23.0-0.1.hum1
```

`--stream 9.6` or `--stream "RHEL 9.6"` limits it to one stream, `--package kernel` to a package, `--json` prints the records. `--list FILE` searches Red Hat's full list instead of the index, so it answers for any CVE, not only the ones the READMEs name; `verify --list FILE` does the same for the installed packages. The exit code is 1 when nothing is found, and what it prints then is "no advisory in the list", which is not the same as "not affected".

## Verify

Give it package names as `name-[epoch:]version-release[.arch]`, from `rpm -qa`, on standard input with `-`, or let it call rpm itself with `--rpm`:

```
$ rpm -qa --qf '%{NAME}-%{EPOCHNUM}:%{VERSION}-%{RELEASE}.%{ARCH}\n' | rhsa.py verify -
$ rhsa.py verify --rpm                      # the same, in one step
$ rhsa.py verify --rpm kernel --cve CVE-2026-98432
```

```
VULNERABLE             kernel-5.14.0-570.153.1.el9_6.x86_64  RHEL 9.6: older than kernel-5.14.0-570.154.1.el9_6, which fixes CVE-2026-98432 (RHSA-2026:94438)
FIXED                  kernel-core-0:5.14.0-570.154.1.el9_6.x86_64  RHEL 9.6: at or after the fix for CVE-2026-53266, CVE-2026-68121, CVE-2026-74469 and 3 more (RHSA-2026:71327, RHSA-2026:71631, RHSA-
CHECK BY HAND          php-cli-7.4.33-1.module+el9.6.0+1.x86_64  the advisories for RHEL 9.6 are for other version lines of php-cli (8.0.30, 8.2.28, 8.3.19), not for 7.4: a release on another line can
NO ADVISORY FOR STREAM cri-o-1.31.2-1.rhaos4.18.el9.x86_64  advisories name cri-o, but none for RHEL 9 rhaos4.18; they are for RHEL 8, RHEL 9, RHEL 9.2, RHEL 9.4, RHEL 10 rhaos4.21, RHEL 8 rhaos4.12 a
verified 4 package(s): 1 older than a Red Hat fix. A listed fix is a fact about the release; whether the flaw is reachable on your host is another question.
```

The exit code is 1 when a package is older than a Red Hat fix, 0 otherwise. `--all` also lists packages that no advisory names.

The tool says what it knows and nothing more. It compares releases the way rpm does (`rpmvercmp`, with the epoch, `~` and `^`), and only under these rules:

1. **Same stream.** The stream is read from the release: `el9_6` is RHEL 9.6, `module+el9.6.0` is RHEL 9.6, `hum1` is a Hummingbird build, `el9sat` and `el8ap` are named as variants. A package on a stream with no advisory is reported as such, with the streams that do have one. It never compares across streams.
2. **Same product release.** OpenShift builds name theirs (`rhaos4.18`, `rhaos4.21`); those are different products, and a release number on one proves nothing about the other.
3. **Same version line.** PHP 8.0, 8.2 and 8.3 sit side by side in one RHEL stream as modules. A fix for 8.0 says nothing about 8.2, so the tool compares within `major.minor` and says "check by hand" when only other lines have an advisory.
4. **No bundles.** An advisory that lists more than 8 source packages (the OpenShift bundles list up to 196) does not say which package fixes which CVE, so it is never used to pair a package with a fix. `--max-packages N` changes the limit. A package only a bundle names is reported as "check by hand".
5. **The lowest fix counts.** When several advisories name a CVE for a package in one stream, the earliest fixed release is the fix.

A verdict is a fact about the release. Whether the flaw can be reached on your host (a module that is not loaded, a service that is not exposed) is another question.

## Refresh the data

`rhsa.py fetch --after 2026-11-03 --out LIST.json --merge LIST.json` downloads Red Hat's list from its Security Data API and adds it to an existing one; `rhsa.py find CVE --live` asks the API about one CVE. They are the only commands that use the network. They expect the `cvrf.json` endpoint of the Security Data API (parameters `after`, `before`, `cve`, `per_page` and `page`; fields `RHSA`, `severity`, `released_on`, `CVEs` and `released_packages`), and `--url` points them at another server.

Red Hat's list comes as a CSV or a JSON file with these columns: `Release Date`, `RHSA`, `Severity`, `Synopsis`, `CVE Count`, `CVEs`, `Packages`, `Advisory URL`, `CSAF URL`. The list of advisory and CVE pairs is optional: the CVEs are read from the `CVEs` column, and a pairs file is only compared with them (the tool says whether it agrees).

```
rhsa.py index LIST.csv --repo ../..        # or LIST.json; PAIRS.csv may follow LIST
rhsa.py docs  --repo ../.. --write         # the README sections and REDHAT-ADVISORIES.md
rhsa.py audit --repo ../..                 # nothing may be out of date, unplaced or unknown
python3 ../gen-site.py ...    # then the documentation site, as for any README change
```

`index` keeps the advisories of every CVE that the READMEs under `--repo` name, plus those in `placement.json`, so a new tool README is picked up; `index --all` keeps every CVE in the list. `audit` fails when a README names a CVE that has an advisory but is not in `placement.json` (place it or exclude it, on purpose), when any file cites an RHSA id that is not in the data, or when a section is out of date.

Streams and packages are read from package names, because Red Hat's list has no synopsis text. That reading is ours, not Red Hat's. The list holds security advisories only (RHSA), not bug fixes or enhancements, and covers one period.
