# Changelog

Notable changes to PrivacySafe Security Patches, newest first.

## 2026-11-23

### Security

- Five scripts ran, as root, a program they had found in a folder another account could write, so a user who planted `node` under `~/.nvm`, or an application account that owns an `/opt` folder, could have had their code run as root during a check. Each now runs such a program as its owner, and as root only when root owns it and every folder above it (`run_found`): [`brotli-oct2026-check.sh`](system/brotli/README.md) 1.3.2 (`node --version`), [`emudhra-mitigate.sh`](system/pki/README.md) 1.1.1 (`node --version` and Node.js's bundled roots), [`curl-oct2026-check.sh`](system/curl/README.md) 1.0.2 (`curl` under `/opt`), [`ghostscript-upload2shell-check.sh`](system/ghostscript/README.md) 1.5.2 (`gs` under `/opt`) and [`expat-check.sh`](system/expat/README.md) 1.1.1 (Python interpreters on `PATH`). Found while checking the new tools for the class of bug behind the symlink report. The new `rf` suite plants such programs and fails if one runs as root; it fails against the previous versions.

### Added

- [Apache Roller XML-RPC deserialization](web-apps/apache-roller/README.md#xmlrpc): new `apache-roller-xmlrpc-check.sh` for CVE-2026-129448 / CVE-2026-82384, a critical (CVSS 9.8) unauthenticated deserialization RCE in Apache Roller 4.0.0 to 6.1.5, actively exploited and in CISA's Known Exploited Vulnerabilities catalog. Roller's XML-RPC servlet ships with the underlying library's `enabledForExtensions` option set to `true`, so it deserializes a non-standard vendor value type carrying a base64-encoded Java-serialized object before any authentication check runs; Roller's own admin-UI toggle for XML-RPC does not gate this on an unpatched install, since the deserialization happens before that setting is ever read. Fixed in Roller 6.1.6, which disables the vendor extension types and adds a new filter that finally makes the toggle work. `check` finds every Tomcat instance this host has the same way `tomcat-oct2026-check.sh` does (explicit `CATALINA_HOME`/`CATALINA_BASE`, running processes' `-Dcatalina.home=`/`-Dcatalina.base=`, then filesystem fallback) and detects a patched install via the presence of the post-fix `XmlRpcEnabledFilter`, since a deployed WAR does not reliably carry its own version number on disk. `hunt` greps access logs for `POST /roller-services/xmlrpc`. `mitigate` applies either of Apache's two named workarounds: `enabledForExtensions=false` by default (no real cost, since it only disables the dangerous vendor extension type), or `--remove-mapping` to comment out the servlet mapping entirely (a real cost, since it also disables the legitimate Blogger/MetaWeblog API, so this option is gated behind confirmed exposure unless `--force` is given). `--dry-run` previews either change; `--restart` restarts a detected Tomcat unit. `rollback` (with its own `--dry-run`) restores. Version 1.7.0.
- [Ghostscript Upload2Shell](system/ghostscript/README.md#upload2shell): new `ghostscript-upload2shell-check.sh` for CVE-2026-125396, a `-dSAFER` sandbox escape via a crafted Type 1 font in the `.putgstringcopy` procedure, reached through ImageMagick, Pillow, WordPress, Roundcube, CUPS and more by file content rather than name or extension; fixed in Ghostscript 10.08.0. `check` cross-references installed packages against each distribution's own fixed-build list and flags a real trap: Ghostscript's own 10.08.0 release candidate, built before the fix commit, reports the identical version string as the real release, so an exact match with no owning package is reported as undetermined rather than clean. It also audits ImageMagick's `policy.xml` for whether the coders `mitigate` would block are already blocked. `mitigate` adds the long-standing community-documented `policy.xml` lines blocking the `PS`/`PS2`/`PS3`/`EPS`/`XPS` coders (`--include-pdf` also blocks `PDF`), gated behind confirmed exposure (`--force` to override) since blocking these coders has a real cost to legitimate PostScript/EPS/XPS processing; `--dry-run` previews regardless of exposure. `rollback` (with `--dry-run`) restores. `rules` covers what `mitigate` cannot automate: the Pillow `formats=` argument, WordPress's and Roundcube's separate upload-path fixes (the Roundcube one already checked by this collection's own `roundcube-oct2026-check.sh`), and print-queue authentication. Version 1.5.0.

### Security

- [Linux kernel](system/linux-kernel/README.md#kvm-guest-to-host-escape-on-amd-nested-virtualization-cve-2026-99312): `linux-kernel-kvm-escape-check.sh` 1.0.1 fixes a link-following race (CWE-59, CWE-377) in `mitigate --unload`, reported privately by an outside researcher. Version 1.0.0 sent `modprobe`'s error output, as root, to `/tmp/psf-kvm-rm.PID` and `/tmp/psf-kvm-ins.PID`. The process id is visible to every local user, so an unprivileged user could place a symlink at that path first and have the root run truncate and overwrite any file root can write (`/etc/shadow`, a cron file, a systemd unit) with `modprobe`'s message. It does not raise privileges or disclose data; it is an integrity and availability flaw, rated Low (CVSS 4.0 about 3.7). The output is now captured in a variable, so nothing is written under `/tmp`. Only `mitigate --unload` on a multi-user host was affected; `check`, `rules`, `rollback` and `mitigate` without `--unload` never reached that code.
- A sweep of every script for the same pattern found two more and closed them the same way: `apache-mod-http2-check.sh` 1.1.1 (the running module list read by `check`, and the `apachectl -t` output in `mitigate`, both went through a PID-based `/tmp` file) and `etherpad-static-traversal-check.sh` 1.1.1 (the `nginx -t` output in `mitigate`). The Etherpad tool also now removes its one `mktemp` file on exit, like the rest of the collection.
- `claude-code-vsx-oct2026-check.sh` 1.3.2: `clean`, run by a user with no `HOME` set and no `BACKUP_ROOT`, fell back to a fixed folder under `/tmp` for the files it moves aside, which another user could create first. It now stops and asks for `BACKUP_ROOT`, and refuses a backup folder it does not own.

When sshd on musl libc checks a password itself (no PAM, or PAM with `UsePAM no`), it hashes the attempt with `crypt()` and compares the result to the account's stored field. musl's `crypt()` returns the literal string `*` for a password over 256 bytes, and `*` is also the stored field of every account with no password, so a 257 to 1024 byte password matches, for any such account, as long as another local account has a `$5$` or `$6$` hash to lend a salt. The 256/257 byte boundary was confirmed against a real musl build. `check` reads sshd's ELF interpreter and dynamic section to judge musl and PAM without executing it, reads the effective configuration with `sshd -T`, and flags a `Match` block that re-enables password authentication on its own, confirmed against a real sshd to happen even under a global `PasswordAuthentication no`. `hunt` reads the auth log and journal for an accepted password login naming a currently no-password account. `mitigate` sets `PasswordAuthentication no` as a drop-in or, where `sshd_config` has no `Include` for it, at the top of the file, and also patches every other explicit `PasswordAuthentication ... yes` line it finds, including one inside a Match block; `rollback` undoes it. The fix is OpenSSH 10.6p2.
- [APT package downloads swapped after verification](system/apt/README.md#apt-nov2026-check) (CVE-2026-109518, 4 November): `apt-nov2026-check.sh`. APT can merge two package downloads when an HTTP redirect gives them the same address and reuses a file through a hard link when it retries, so someone who can alter the HTTP traffic (an attacker on the network path, a malicious mirror or a proxy) can replace a package after APT has verified it, and the replacement is installed as root. It needs both a redirect and a retry: `Acquire::Retries` is 3 by default on Debian 12 and Ubuntu 22.04 and later, so older releases are not exposed unless something turned retries on. `check` judges the installed APT against the fixed release of its line (3.3.6, 3.2.1, 3.0.4, 2.8.4, 2.6.2, 2.4.15, 2.2.5 and the older lines of the CVE record, and the Ubuntu builds that fix a line below those), reads the effective retry and redirect settings through `apt-config`, and lists the sources that use plain http; it exits `1` only when the version is vulnerable and both conditions are on. `hunt` compares cached packages with the SHA-256 in the index and looks for hard-linked files in the package and list caches, and says plainly that no indicator is published. `mitigate` writes one file in `/etc/apt/apt.conf.d` that sets `Acquire::Retries` to 0, confirms the effective value with `apt-config` and removes the file again if another setting wins; `rollback` removes it. Updating APT is the fix, and the README gives the update command with retries off for the update itself.

### Fixed

- [PHP session audit](runtimes/php/README.md): a risky session serializer (`php_binary` or `php_serialize`) on its own, with upload progress off and no runtime switch in the code, exited `0` and printed "No precondition found", although its usage defines exit `2` as a partial match and the same run had already reported condition 1. It now exits `2` and says it is a partial match.
- [libheif checker](system/heif/README.md): the `policy` check judged a coder blocked when a policy file was written on one line, because one element's `rights="none"` could vouch for another element's pattern (a `delegate` or `path` policy made HEIC look blocked). Each `<policy>` element is now judged on its own. `harden`, `unharden`, `mw-harden` and `mw-unharden` put each backup in a directory named only by the second, so two runs in one second overwrote the original backup with an already-edited file. Every backup now has its own private directory (mode `0700`, which also keeps a `LocalSettings.php` copy, with its database credentials, from being world-readable). `hunt` reported clean when it could read no journal or log; it now exits `2`.
- [Collabora CODE mitigator](web-apps/nextcloud/README.md): any option it did not recognize was silently ignored, so a mistyped or invented flag such as `restore --dry-run` ran a real restore. Only `--force` is now accepted and anything else exits `2`. `hunt` reported clean (exit `0`, with an "ok" line) when there was no app folder and no readable log. It now exits `2` and says nothing was searched.
- [Ruby checker](runtimes/ruby/README.md): `scan` reported a clean result (exit `0`) when none of its scan paths existed, and `hunt` did the same when it could read no journal or log, so a search with no data looked like a clean one. Both now exit `2` and say nothing was read. A Discourse version such as `3.4.0.beta1` was displayed as `3.4.0.`. It is now shown in full.
- [Sentry for Next.js](developer/sentry/README.md), [Storybook](developer/storybook/README.md) and [Laravel](developer/laravel/README.md): a pre-release of a fixed release (`10.75.2-rc.1`, `8.6.19-rc.1`, `12.68.0-RC1`) was judged fixed, because the status functions compared only the numeric part (and Laravel's `norm_ver` dropped the suffix). A pre-release comes before the release it leads up to, so it now reads as not fixed. A pre-release above the fixed number, and the fixed release itself, are judged as before.
- Known limit, stated in the release notes: the checkers that normalize with the shared `norm_ver` helper compare only the numeric part of a version, so a pre-release of exactly the fixed number can read as fixed in those that were not individually checked.
- [PHP2Shell on cPanel](runtimes/php/README.md): a release candidate, beta or dev build of a fixed release (`8.4.27RC1`, `8.4.27beta2`, `8.4.27-dev`) was judged patched, because the version comparison sorts those after the final release although they come before it, so `check` exited 0 and `cleanup` would reduce the drop-in on a build that is not fixed. Such a build is now judged by its numeric part and reads as patched only above the fixed number.
- [eMudhra mitigation](system/pki/README.md): a certificate file moved out of `/usr/local/share/ca-certificates` or `/etc/ssl/certs` was kept under its bare file name, so two different files with the same name from different directories overwrote each other in the backup and `restore` would then have put the wrong certificate back. Each is now kept under a numbered name. Backup directories were named only by the second, so two runs in one second shared one and the second overwrote the first run's copy of `ca-certificates.conf`. The process id is now part of the name.
- [PHP2Shell mitigation](runtimes/php/README.md): `remove` backed up the AppArmor profile, your local override and the disable link into one directory under the same file name, so each copy overwrote the previous one and the site-specific rules in the local override were lost (with a disable link present, only the link survived). Each now has its own name. Backup directories were named only by the second, so two runs in the same second overwrote the first backup. The process id is now part of the name. The message printed when the generated AppArmor profile fails to parse said "nothing installed" although the ini drop-in from step 1 had already been written. It now says what was and was not changed. The undocumented `PHP_VER` environment variable, which limits a run to one version like `--php`, is documented.

- Every README now has a "know before you run it" section. The 33 that lacked one (the newer checkers and a middle group of older ones) now list what the tool is and is not, drawn from each script's own stated scope: the fixed versions, what a version number cannot show, what it reads, which flaws are conditional, and where a hunt exists or does not.
- [LiteLLM checker](developer/litellm/README.md): a scan path that exists but cannot be read left `check` reporting clean (exit `0`) although its usage promises exit `2` for something it could not read. It now exits `2` when nothing else is found.
- [GhostAction checker](developer/ghostaction/README.md#before-you-run-it): `check` reported itself as a C2 indicator (exit `1`, "credentials may be stolen") when run from the directory it was downloaded to, because its own text names the domains. It now leaves its own file out. It also reported a clean result (exit `0`) when every scan path was missing, and its usage promises exit `2` for something it could not read: that is now implemented. `hunt` wrote `crontab -l` output to a fixed file in `/tmp`. It now uses a private temporary file.
- [Plex checker](web-apps/plex/README.md#before-you-run-it): `hunt` reported any copy of its own script found under a scanned scratch directory. It now leaves out the running file. New `HUNT_ROOTS` setting for the directories `hunt` searches.
- [Node.js mitigator](runtimes/node/README.md#before-you-run-it): `status` exited `1` when the installed guard matched the shipped one, which is the healthy case; it now exits `0`.
- Runtimes found only on `PATH` were never found. The curl, nginx, Ruby and Brotli (Node.js scan) checks and the Node.js mitigator searched `PATH` with `command -v -a`, which is not a valid option in bash and failed silently, so only a fixed list of locations was searched. A Node.js, Ruby, nginx or curl installed elsewhere on `PATH` was reported as not present. They now use `type -a -P`.
- Pre-releases and non-version text were judged fixed. In the Brotli checker, a `node` that printed `v24.22.1-pre`, `-rc.0` or `-nightly…` was reported fixed at the fix version, and one that printed text (an error from a broken version-manager shim) was reported fixed because non-numeric text sorts after every number. The same function judges Bun, Envoy, Istio, cdxgen and the Ruby and PHP Brotli extensions. A `-dev` suffix was also damaged before it was judged (every `v` was removed from the output). All of these are now reported as unknown. The Node.js mitigator dropped a pre-release suffix the same way and now keeps it. A runtime it cannot judge on disk makes `check` exit `2`, as its README says.
- One unreadable binary could end a whole check. Under `set -e`, an unreadable `curl` (or a `node` that printed no version) made the curl check and the Node.js mitigator stop silently after a few lines with exit `1`, so later findings, such as a vulnerable libcurl, were never reported and the status looked like "vulnerable". The PKI mitigator did the same, with exit `3`, when `openssl` failed during its certificate self-test. All three now report the problem and finish.
- [curl checker](system/curl/README.md#before-you-run-it): a development build (`8.20.2-DEV`) at a fix version was reported as fixed. It is now reported as unknown, because it is a build made before the release.
- [WordPress XSS2Shell checker](web-apps/wordpress/README.md#wordpress-xss2shell-check): `check` and `audit` now stop with exit `2` when no URL is given, instead of relying on `curl` failing. `audit` reported a clean result (exit `0`) for a site that did not answer. An unreachable target is now an error (exit `2`), as its usage text always said. Its HTTP response bodies, which can contain an exposed `wp-config.php`, were written to fixed, world-readable files in `/tmp` and left behind when a run was interrupted. It now uses one private `mktemp` file that is removed on every exit path.
- Exit codes. Ten check and mitigate tools (Brotli, curl, GhostAction, libheif, LiteLLM, nginx, Plex, Ruby, the Collabora CODE mitigator and the Node.js mitigator) exited `1` on a fatal error such as a mistyped command or an unknown option, although their READMEs document `2` for errors and `1` means findings. They now exit `2`. The PKI and PHP mitigators keep their own documented exit codes.
- Environment variables that several tools read but did not list (the Brotli per-product fixed versions, `BACKUP_ROOT`, `SCAN_CONTAINERS`, `GUARD_SRC`, `SCAN_DEPTH`, `CODECS_SINCE_DAYS`) are now listed in each tool's `--help`. Two advisory links in the WordPress README pointed at a page GitHub does not serve. They now use the repository advisory address. An unused helper was removed from the Node.js mitigator.
- Pipelines that could miss a match. Under `set -o pipefail`, `producer | grep -q PATTERN` can report "not found" when `grep -q` exits at its first match and the producer dies of SIGPIPE. It needs a producer that writes more than a pipe buffer (about 4 KB) after the match. Twelve scripts used the shape (bind, brotli, curl, drupal, heif, nginx, node, both PHP2Shell tools, pki, and both WordPress checkers), several of them against large sources: `journalctl` in the Node guard-liveness check, `rpm -q --changelog` in the cPanel PHP tool, `openssl s_client` in the PKI tool, and HTTP response bodies in the WordPress probes. Each now reads all of its input and discards the output. What the scripts report is otherwise unchanged.
- Inputs that could pass as clean. In the checkers for Zammad, OpenSSL, the Linux kernel, Jenkins, GitLab, Magento and Mage-OS, an input the script could not trust to be a release no longer ends in a clean result. A pre-release build (`7.2.0-pre`, `3.6.5-dev`, `3.6.0-rc2`, `7.0.13-rc1`, `19.4.2-pre`) at or above a fix boundary is a warning, not the fixed release. An unparsable package version or `openssl` output, and a Jenkins plugin whose manifest has no `Plugin-Version`, are reported as unreadable (exit `1`) and are never skipped. A pre-release below a fix boundary is still judged exposed.
- [nginx-ui checker](servers/nginx-ui/README.md#nginx-ui-check): checks the official `uozi/nginx-ui` container image by tag, and judges a version supplied in `NGINX_UI_VERSION` even when no binary is found on the host. Both were previously ignored, which let a containerized or remote instance report as clean. A `latest` tag is a warning that says the version cannot be read from outside the image.
- [Node.js tool](runtimes/node/README.md#nodejs-october-2026-mitigation): `hunt` exited `1` on a host with nothing to find, although `1` means "findings". A `RETURN` trap that referenced a function-local variable fired again after the variable went out of scope, and `set -u` aborted the script. A hunt with nothing to report now exits `0`.

## 2026-10-21

### Added

- [PHP2Shell mitigation](runtimes/php/README.md#php2shell-mitigation): `php2shell-mitigate.sh` for CVE-2026-109618 and CVE-2026-109619, written the night of 20 October, after exploit details leaked, then confirmed working and published the morning of 21 October, before PHP published its fixes (announced for 14:00 UTC) and before distributions shipped theirs.
